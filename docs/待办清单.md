## G. 索引任务卡死（10-31 18:45 发现）

**现象**：顶部「处理中」一直显示 45/57 不动。

**实测**：

```
audio_vector  processing 45 → 49
text_vector   processing 49
jobs: index_auto_model_ready  running 98/98   ← 卡在这里
      index_auto_model_ready  failed  interrupted 98/98   ×N
```

**机制**：任务把 98 个 artifact 从 pending 改成 processing → 跑到 98/98 就卡住不再结束 →
界面上的「处理中」永远停在这些行上。新任务只看 pending，看不到 processing，于是什么都不做。

**已做的临时处置**：取消卡住的任务 + 把 processing 退回 pending（98 条），再手动触发 reconcile。

**还需要做的（F2）**：

1. 任务失败/取消/中断时，把它认领的 artifact **退回 pending**（现在只留 processing）
2. 查清为什么任务跑到 98/98 就卡住：疑似 mel worker 或解码卡死，
   日志里 `_loop_lag_watchdog` 反复出现，需要抓一次卡住时的线程栈

### F2 追查记录（10-31 19:20）

**已定位**（faulthandler 线程栈实测）：

```
Thread A: core/embedder.py:313 in _rd        ← 读 worker 输出，永久阻塞
Thread B: embedder.py:323 in join            ← _mel_round_trip_locked 等它
          embedder.py:264 _mel_round_trip
          embedder.py:405 _process_chunks
          embedder.py:873 encode_audio_batch
          indexer.py:639 add_audio_batch     ← 索引任务卡在这里
```

即：mel worker 卡死 → 调用方无限 join。原来的 90s 超时 × 2 次重试 = 单块 3 分钟，
98 条待处理要十几分钟，界面上就是「处理中」不动。

**已修**：
1. `MEL_BATCH_TIMEOUT` 90s → 30s（正常块 <15s），卡死块快速进入 kill/二分
2. 看门狗判定任务卡死时，把该工程 `processing` 工件退回 `pending`（此前只有正常退出才回滚）
3. 索引任务启动时挂 `faulthandler.dump_traceback_later(120s, repeat)`，卡死会有完整线程栈

**仍未解决（需要继续）** —— 注：single-flight 与「单批 512 条」已经落到代码里（P1 期间核对过），
下面这条是当时的原始记录，现状请以日志为准：

任务反复出现 `interrupted`：自动索引和手动对账会互相打断，每次启动都把 98 条
一次性认领成 `processing`，被打断后要等看门狗回收，于是形成「卡住 → 回收 → 再来」的循环。

正确做法：
1. **同一工程只允许一个索引任务**（single-flight），新任务不要打断旧任务
2. **认领要小批**（例如一次 8 条），打断时只丢 8 条而不是全部 98 条
3. 处理不动的文件直接落 `failed`，让计数收敛到 0，而不是反复重试

> 库里有手写描述时导入知识包/描述包会**整批写不进去**（界面显示「应用 0 条」，只有一条 warning）。
