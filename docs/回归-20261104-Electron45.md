# Electron 45 回归记录（2026-11-04 夜，构建 r34）

> 这一轮的目标是交接文档里挂着的「Electron 45 功能回归」。
> 结果：先撞到一个「整个程序打不开」的启动阻塞（已修），再撞到一个「一放声音整个程序就消失」的崩溃（定位中，未修完）。

---

## 一、已经修好的：启动阻塞（构建 r34）

### 现象

```
双击 EchoMind.exe → 启动窗停在「启动失败 / 启动超时 · 请重新安装或查看应用日志」
后台后端其实是好的：GET /api/v1/health 返回 200 status=healthy
窗口再也不会出来，只能杀进程
```

截图证据：`_evidence_splash_stuck.png`（启动窗原文）。

### 根因（两个，叠在一起）

| # | 问题 | 说明 |
| --- | --- | --- |
| 1 | **后端版本门禁写成了等号** | `waitForBackendHealth` 要求 `/health` 里的 `version` 严格等于 `app.getVersion()`。应用已经升到 `0.3.0-beta.20`，而后端 exe 还是 11-04 00:28 打的 `0.3.0-beta.19`（改版本号时没重打后端），于是健康检查永远不算通过 |
| 2 | **健康探测预算 120 秒，冷启动要 150 秒** | 195,174 行文件、6.2 GB SQLite、3.2 GB 向量库全部读进来要 2 分半；120 秒一到就判「启动超时」，主窗口直接不建 |

现在 `/health` 的实际返回：

```json
{"status":"healthy","version":"0.3.0-beta.19","device":"cuda","model_loaded":true,"audio_decoder_available":true}
```

### 改法（`main.js`）

```
版本门禁   健康 + 解码器可用就算通过；版本对不上降级成一条告警（只打一次，别刷日志）
           —— 后端 exe 忘了重打不该等于「整台机器打不开」
探测预算   120 s → 300 s
启动窗     每 5 秒滚一次「数据库加载中 37s」，让人看得出程序在动
失败文案   「请重新安装」→「点打开日志看后端输出，重开程序可再试」
```

顺手把 Electron 45 的两条弃用告警处理了：`safeStorage.isEncryptionAvailable` / `decryptString`。
启动时用新的异步接口探一次、结果缓存，同步调用点继续用缓存值，调用链不用全改 async。

> 还剩 `safeStorage.decryptString` 的告警：它本身没有异步替代的必需性，但 Electron 45 也在催 `decryptStringAsync`。
> 这条不影响功能，留到下次一起收拾。

### 验证

```
启动耗时   6 秒出主窗口（后端已热的情况下）；冷启动 150 秒左右也能进
日志       [Backend] ⚠ 后端版本 0.3.0-beta.19 与应用版本 0.3.0-beta.20 不一致，继续启动

## 二、没修完的：一放声音，整个程序消失

### 现象（现在这台机器上，r34 + Electron 45 必然复现）

```
点列表里任意一行  → 4 个 EchoMind 进程全部消失，界面直接没了
进程退出码       0x80000003 (STATUS_BREAKPOINT)  ← 主进程里某个 CHECK 挂了
没有崩溃弹窗，事件查看器里没有记录，用户数据没损坏
```

### 已经排除掉的原因（每条都是实机对照）

| 怀疑对象 | 怎么排除的 | 结果 |
| --- | --- | --- |
| Electron 45 本身的音频管线坏了 | 用官方 electron.exe 45.2.2 跑一个 20 行的小程序放同一段 WAV | 正常播放，退出码 0 → **Electron 45 无辜** |
| 页面/前端脚本的问题 | 用官方 electron 45 加载本项目自己的 `index.html` + `preload.js`，再放 blob 音频 | 正常播放 t=0.2 rs=4 → **前端脚本无辜** |
| `sandbox: true` | 小程序开/关 sandbox 各放一次 | 都正常 |
| CSP（`webRequest.onHeadersReceived` 全量注入） | 小程序里注入同样的 CSP 再放 | 都正常 |
| 自定义协议 `protocol.handle` 的 Response 写法 | 小程序注册同名 scheme，分别用 `new Response(Buffer)` 和 `net.fetch(file://)` | 两种都能播 |
| GPU | 主程序加 `--disable-gpu` | 照样崩 |
| 沙箱总开关 | 主程序加 `--no-sandbox` | 照样崩 |
| 后端占用音频设备 | 起界面后杀掉 soundbot-backend 再放 | 照样崩（后端还会被看门狗拉起来） |
| MediaSession 服务 | 主程序加 `--disable-features=MediaSessionService` | **不崩了**，但音频加载返回 `err=4`（SRC_NOT_SUPPORTED），放不出声 |

结论：触发点在**主进程的某处配置**，不是 Electron、不是前端、不是解码器本身。
`MediaSessionService` 那条能把「崩」变成「加载失败」，说明崩溃就发生在 Chromium 的媒体会话/音频输出这一段。

### 复现命令（下个会话直接跑）

C:\Users\cj\.dsh\dsh-runtimes\dsh-primary-runtime\dependencies\node\bin\node.exe scripts\audio_crash_probe.mjs
```

输出 `进程数 = 0 → 崩了 ❌  退出码 = 2147483651 0x80000003` 就是复现了。

### 下一步该往哪查

```
1  main.js 里逐段注释掉「非必要」的主进程初始化（托盘、菜单、TTS 本地服务、更新器、浮窗 IPC），
   每砍一段跑一次 audio_crash_probe.mjs，二分到那一段
2  重点看：spawn 子进程、session 级设置、globalShortcut、nativeImage/Tray
3  如果实在二分不出来：回到 Electron 28.3.3（升级前的版本，天天在用）
```

## 四、追加（20:50，构建 r35）：找到放不出声的真凶了

### 一句话

`protocol.registerSchemesAsPrivileged` 里少了 `stream: true`。

少了它，`<audio>` 走 `soundmind-audio://` 加载一律判「不支持的源」（`err=4`）：
Electron 28 上表现为放不出声，Electron 45 上直接把主进程 CHECK 挂掉（0x80000003）。

对照实验（官方 electron 45.2.2 起迷你程序，同一个协议名、同一个 WAV）：

```
privileges 带 stream: true   →  rs=4  正常播放，err=null
privileges 不带 stream        →  rs=0  err=4
                                （Electron 28 停在这一步；Electron 45 继续崩）
```

### Electron 45 仍然崩

加上 `stream: true` 之后，Electron 45 上「协议加载」和「blob 加载」两条路仍然 0x80000003。
所以 45 的崩溃是另一层原因，不能靠协议开关盖过去，今晚不硬啃。

### 追加：r36（协议改用 net.fetch）

```
改动   protocol.handle 里不再 readFile 再包 Response，改成 electronNet.fetch(pathToFileURL(路径))，
       失败才退回读 Buffer 的写法
理由   读 Buffer 包出来的响应没有总长度，播放条算不出时长
结果   声音正常；但 mp3 的时长仍然显示 Infinity:NaN:NaN（dur=0）
结论   stream: true 会让响应变成分块传输，Chromium 拿不到 Content-Length 就估不出 mp3 时长。
       这是「能听、但进度条不显示总长」的瑕疵，先记着，不影响放声音
```

> 猜测：老版本用的是 `protocol.registerFileProtocol`（真文件语义，带长度和支持拖动），
> 11-04 为兼容 Electron 45 换成 `protocol.handle` 之后丢的。下次可以试着判断
> `typeof protocol.registerFileProtocol === 'function'` 就先走文件协议。
