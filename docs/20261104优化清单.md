## 二、功能新增

| # | 功能 | 说明 |
|---|---|---|
| F1 | **移动到文件夹…** | 主列表右键，把选中的音频在磁盘上真移动到音效库其他目录；库内路径同步，file_uuid 不变，标签描述索引全保留。支持多选、目录搜索、失败逐个回报 |

**后端接口**

```
POST /api/v1/db/files/move
  { file_uuids: [...], target_dir: '...', overwrite: false }
  → { moved: [...], failed: [...], moved_count, failed_count }
```

**安全措施**

```python
shutil.move(source → target)
try:
    UPDATE files SET path=?, canonical_path=?
except:
    shutil.move(target → source)   # 库没写成就把文件挪回去
    raise
```

## 四、事故记录

### 11-04 上午：测试脚本删掉 3 个真实音频

```
起因：测移动接口时直接拿用户库里的文件做实验
过程：shutil.move 成功 → UPDATE files 报 no such column: folder
     → 数据库没更新，文件已进临时目录
     → 测试脚本 finally 里 rmtree 删了临时目录
结果：3 个 wav 永久丢失，回收站和全盘搜索都找不到
     F:\CJ音效库整合包V1\_待人工判断\Eelectronic woosh.wav
     F:\CJ音效库整合包V1\转场与设计\掠过\Speeder.wav
     F:\CJ音效库整合包V1\转场与设计\掠过\Swish grainy.wav
```

**三条铁律（已写进开发规范）**

```
1  测试绝不在用户真实数据上跑，一律自造临时文件
2  涉及真实文件的操作，数据库失败必须回滚文件
3  绝不自动删除用户文件，删除一律走回收站
```

### 11-04 上午：更新器死循环

```
现象：装了好几次更新包都报「版本不匹配」，或者装完没变化，还一直闪黑框
根因：更新器把新文件写成 app.asar.updating，等程序退出后替换，
     但替换那一步从未成功，每次都留一个 .updating 文件
     r27 本来要修这个问题，但 r27 自己就是靠这个坏更新器装的，形成死循环
解法：手动把 app.asar.updating 改名成 app.asar，打断循环
```

### 一个差点被忽略的坑：装包看不出版本

```
现象：每次装完更新包，界面上「已是最新版本 v0.3.0-beta.19」不变，
      无法判断新包到底装进去没有，导致同一个问题修了三遍都没生效。
根因：package.json 的 version 一直停在 beta.19（用户要求不动版本号），
      而那个提示来自远程 update.json 的 latest 比对，本来就不反映本地构建。
解决：加 build.buildStamp，每次打包递增，检查更新时显示「构建 r32」。
```
