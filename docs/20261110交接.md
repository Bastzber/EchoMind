## 五、今天（11-10）踩的坑 —— 这一节最值钱

### 5.1 「保存失败：文件不存在」的连环套（花了四轮才彻底查清）

现象：改完名保存标签，报「文件不存在」，但文件明明在列表里。

**根因是三层叠在一起**：

```
第一层  数据库里 4215 条 canonical_path 用反斜杠，重算用正斜杠（历史数据）
第二层  rename_file（单条重命名）只改 filename，不改 path / canonical_path
第三层  files.py 的批量重命名只改 path / filename，漏了 canonical_path  ← 真正的元凶
```

**canonical_path 是什么**：小写规范化的路径，所有「按路径查」都用它——
保存标签、改描述、再次重命名、播放。它和 path 必须同步，
否则界面显示正常但查不到。

**已修**：

```
database 数据     全库重算，现在 195451 条 0 条不一致
db_files.py       rename_file 改成三者一起更新
files.py:142      批量重命名补上 canonical_path
```

**遗留待观察**：修完之后还没让老板完整验证「批量重命名 + 保存标签」这条链路。

### 5.2 改了 Python 从不重新打包（这是最大的一次失误）

连续几次改完后端逻辑就直接发更新包，只换了 app.asar。
后端是 PyInstaller 编出来的 exe，**源码改动一个字都不会进到 exe 里**。

表现：老板反复说「还是不行」，其实改的东西压根没跑起来。

**判据**：搜 exe 二进制看有没有新模块名，或者直接看 exe 文件时间戳。

### 5.3 保存成功了但列表不刷新

列表的数据源是分页加载的 `soundData`，详情面板手里那个对象
**有时不是数组里的同一个**。改了 `sound` 再 `renderSoundList()`，
列表看的是另一份，所以看不出变化。

**修法**：按 id 在 soundData 里找到对应那条覆盖，再重绘。
已改：标签、用户标签、一句话描述、重命名，四处统一。

### 5.4 索引一跑，所有操作都卡

一把「工程锁」保护整个工程，索引任务持有几十秒到几分钟，
用户改一行标签也得排队，界面一直转「保存中」。

**修法**：

```
_SoftIndexLock   最多等 0.6 秒，拿不到就绕过（WAL 模式写安全）
已换            改标签、改名、删标签、重命名、重新分析、删文件、文件夹增删改
索引任务本身    仍然拿真锁（导入/重扫/修复那三处），那里必须真互斥
```

### 5.5 改一次标签排一个全量重建任务

改 23 次标签 → 排 23 个「文本向量重算」任务 → 界面显示「处理中 23」→ 互相抢锁。

**修法**：`create_job` 加去重，同工程同类型已有活跃任务就复用 id。

### 5.6 中文逗号

标签输入支持 `, ， 、 ; ；` 五种分隔符。
只有「重复文件」面板原来只认英文逗号，已统一。

### 5.7 长音频克隆效果差（真因不是软件 bug）

实测数据（232 字那段）：

```
Breeze 默认             91.8 秒   2.53 字/秒   静音 20.2%
Breeze + 中文指令       91.8 秒   2.53 字/秒   ← 中文指令模型不认，反而更慢
Breeze + 英文指令       67.7 秒   3.43 字/秒   ← 英文指令有效
再加后处理(1.3倍)       54.5 秒   4.26 字/秒   ← 正常语速
VoiceStudio 同段        58.5 秒   3.97 字/秒
```

**结论**：

* 音色描述框里写**英文**指令（`Speak fast, crisp and clear delivery.`），中文指令无效
* 后处理（`tts_postprocess.py`）压静音 + atempo 提速，音高不变
* 音量三个引擎基本一致（RMS 都在 -17.5 dB 上下），不是音量问题
* 语速慢的根子是模型本身 + 参考音频的语速被克隆学了进去

### 5.8 peaks_json 一个字段吃掉 79% 的库（11-10 深夜解决）

现象：库 3.32 GB，6.5 万个文件，按理不该这么大。

查下来：

```
peaks_json 合计   2.62 GB / 3.32 GB = 79%
平均每条          39.8 KB（2000 个点）
单点长这样        3.1982603104552254e-05   ← float32 被 json 展开成 17 位有效数字
```

**根因**：`json.dumps(np.float32 序列)` 会把 float32 的完整十进制展开写进去。
渲染端只是把 2000 个点画成像素柱，3 位小数都过剩。

**修法**（这一轮做完的）：

```
core/db_common.py     新增 serialize_peaks()：round(3) + separators=(',',':')
写入点全换            main.py ×2、database.py、db_common.py、db_files.py
数据迁移              scripts/slim_peaks.py（--dry-run 量尺寸，--apply --vacuum 落地）
```

**结果（实测）**：

```
peaks_json   2.619 GB → 0.740 GB   省 1.88 GB（71.8%），65119 条全部变短
库文件       3.32 GB → 1.05 GB    VACUUM 10 秒
点位数       迁移前后都是 2000 个/条，integrity_check = ok
```

**回滚**：拷回 `C:\Users\cj\AppData\Roaming\EchoMind\db\soundmind.db.bak-peakslim-20261110`
（3.32 GB，做迁移前的完整备份，integrity_check 已验）。
代码回滚 `git revert` 之后必须重新 PyInstaller 打包，否则 exe 里还是新逻辑。

### 5.10 索引遇到坏文件：现在直接跳过（终态）——11-11 凌晨做的

改之前：任务自己取活用的是 `states=("pending","failed","stale")`，**failed 也算待办**。
于是 32 个解不开的文件每轮都被重新捡起来，实测一轮白等 **632 秒 / 31 条 = 20.4 秒/条**，
全是「30 秒批超时 + 20 秒单文件重试」的罚站，正常文件 0.26 秒/条。

改之后：

```
worker 明确报解码失败（decode_error / decode_timeout / unsupported…）
  → error_code = 'decode_failed'（终态）
  → list_artifacts_for_work 默认跳过这个码（任何自动对账都不再碰）
  → 顺手记进毒名单（两次才拉黑，防误封）
```

逃生口：单条右键「重新分析」会先把 error_code 清掉，所以真想救某个文件仍然能救；
`--rebuild` 重建索引也不会被这些文件拖住。

线上落地的数据侧动作（11-11 00:10）：

```

毒名单 poison_files.txt 从 84 条清理成 30 条
  → 旧 84 条里有 20 条是误封：那些文件现在都有正常向量，重建时会被白白跳过
  → 回滚清单：E:\AI音效管理器\decode_failed_migration_20261111.json
部署后（00:10:49 exe）实测：20 秒内 0 个新任务、后端 CPU 增量 0 秒/15 秒、
日志里 23:59:38 之后再没有一条「[索引] 音频失败」
```

### 5.11 14 秒的任务底座 → 改成「用户停手后合并执行」

改之前：改一次标签 / 生成一条描述 / 改一次名，都立刻排一个 `text_metadata_refresh` 任务。
每排一次就付一遍任务底座 **约 14 秒**（模型只占 4 毫秒），连续改十条就白跑十遍。

改之后：`_defer_user_index()` 防抖调度

```
停手 6 秒才开跑（_USER_EDIT_QUIET_SECONDS）
最长推迟 45 秒（_USER_EDIT_MAX_DELAY_SECONDS，一直不停手也不许无限拖）
连续改动合并成一个任务：job kind = index_auto_user_edit
```

隔离实例实测（5 次连续保存标签）：

```
接口每次        0.22 ~ 0.29 秒返回（不会被索引卡住）
新建任务        1 个（total=5，最后一次保存后约 6 秒出现）
以前            5 个任务，每个 14 秒级
```

**还有一个坑必须一起修**：如果改动落下时正好有任务在跑，那个任务的取活清单是改之前
取的，这批改动就漏了。所以 `_fire_user_edit_index` 发现「已有任务在跑」时不丢改动，
而是 `_rearm_user_edit` 挂 8 秒后重试——等它跑完补一轮，不会静默丢索引。

### 5.12 自动续跑的无限自转（顺手修的）

`_run_automatic_reconcile` 原来无条件链式续跑。只要有一批永远失败的工件，
任务就每 3 秒自转一次：**实测 20 秒内排了 18 个任务**，CPU 白白烧着。

现在：一轮里一条都没成功 → 退避 20 秒 / 40 秒，连续 3 轮没进展就停，日志写明原因，
剩下的交给手动「修复索引」。
