# 长 ID3 MP3 音频向量失败 · 根因与修复（2026-10-31 深夜）

> 交接文档第三节说的「下一步：在 main.py 7688 加日志，看是 batch_encode 返回空还是没被调用」
> —— 不用猜了，日志早就指明了方向，真正的原因在 **melworker 子进程**里，一行解包写错。

## 一、结论（一句话）

`backend/core/melworker.py` 的常驻 worker 主循环里，
`_process_one()` 返回的是 `(features, reason)` 二元组，但代码写成了

```python
feats = _process_one(...)            # ← 拿到的是元组，不是 features
vec = _forward_one(model, feats)     # _forward_one 里 features.get() 抛 AttributeError
```

`_forward_one` 的 `except Exception: return None` 把异常吞了，于是
**每一个文件都返回 None**。父进程只看到「批量编码未产出向量（原因: unknown）」，
既不是解码失败，也不是超时，更不是模型限制——**签名/ID3 跟这件事无关**。

## 二、证据链（都是实测）

| 步骤 | 结果 |
|---|---|
| 主进程 `_process_one`（同一份代码，正确解包） | ✅ feats 正常，`input_features (1,1,1001,64)` |
| 主进程 `_forward_one(model, feats)` | ✅ `(1, 512)` |
| 主进程 `_forward_one(model, (feats, ""))` | ❌ `None`（复现 tuple 传入的效果） |
| 走 worker 协议（修复前，源码） | ❌ 正常文件 + 目标文件**都**返回 None |
| 走 worker 协议（修复后，源码） | ✅ 两个文件都返回 `(1,512)`，范数 1.0 |
| 走打包 exe `soundbot-backend.exe --mel-worker`（修复后） | ✅ 同样两个文件都返回 `(1,512)` |

关键交叉验证：**对着一个本来就 ready 的正常文件（10. geoff zanelli - Medal Of Honor）
也返回 None**——说明不是这个 MP3 的问题，是所有走 worker 的编码都坏了。
之前的排查一直被「只有这一个文件 failed」误导：其实库里 64,873 条 ready
是更早的版本编出来的，本轮只有这 1 条待补，所以症状看起来「只坏一个文件」。

## 三、改动

| 文件 | 改动 |
|---|---|
| `backend/core/melworker.py` | `_main()` 正确解包 `feats, reason`；失败时回传 `{"error": reason}`（父进程能拿到真实原因，不再 unknown）；`compute_mel_batch()` 里「慢 ≠ 失败」的错误分支修掉（原来 >3s 的文件会被写成 error） |
| `backend/core/embedder.py` | 被毒文件黑名单/运行时黑名单拦掉的路径，记 `_MEL_FAIL_REASONS[path] = "blacklisted" / "runtime_blacklisted"`，不再静默返回 None |
| `backend/main.py` | 批量落库失败时的 `error_message` 带上 worker 回报的原因（原来只有「批量编码未产出向量」） |
| 数据（用户目录，非代码） | `%APPDATA%\EchoMind\poison_files.txt` 删掉目标文件的那一行（见下） |

### 为什么还要清黑名单

tuple 缺陷的连带后果：文件在 pass 2 二分里被判成「毒文件」，
`_note_bad_file()` 写进了 `poison_files.txt`（2 字段 + 时间戳，3 天有效）。
**修好代码也不会自动解封**——`encode_audio_batch` 一进来就被黑名单过滤掉，
秒返回 None。所以必须删除这一行。

原文件已备份：`poison_files.txt.bak-20261031-223315`。

> 顺带发现的坑（未改）：`main.py` 的单文件超时分支写的是 3 字段
> `path\tts\t1`，而读取端 `float(ts)` 会因多出来的 `\t1` 抛 ValueError
> 而被当成「无时间戳 → 不信任」。也就是说**超时路径写的黑名单从来没生效过**。
> 这次不改是故意的：今天这条假黑名单就卡了一个正常文件，宁可漏封也别误封。
