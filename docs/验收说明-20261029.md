## 六、本轮补充：B1 / B2 / B3

### B2 取消真正生效（改了）

原来取消只在"逐个工件"的循环里检查，编码是攒批做的 —— 一批 4 个文件正在编码时取消不生效，
要等这批跑完。现在**每个落库块之间都检查一次** `cancel_requested`：

- 音频块（`AUDIO_FLUSH_CHUNK=4`）之间：命中取消 → 把还没处理的工件退回 `pending`（不是 failed）→ 任务标 cancelled 返回
- 文本块（`TEXT_BATCH=32`）之间：同上

### B1 mel-worker 超时（改成可配）

原来硬编码：块超时 600 秒、单文件回退 90 秒。现在可通过环境变量调：
`ECHOMIND_ENCODE_CHUNK_TIMEOUT`（默认 300）、`ECHOMIND_ENCODE_SINGLE_TIMEOUT`（默认 60）。

保留原有行为：块超时 → 释放 GPU → **拆成单文件逐个重试**（单文件 60 秒）→ 仍超时的记入毒名单并标 failed，同批其它正常文件照常入库。

### B3 状态一致性（补了一处）

启动自愈（`processing → pending`）本来就有。本轮补的是**任务异常退出时的回滚**：
`_repair_index_task` 加了 `finally`，任务不是正常完成（失败/取消/异常）时，把本轮标成
`processing` 的工件退回 `pending`，避免这些行既不被重试、也不显示为失败（数字冻结的成因）。

### 实测

重启应用验证自愈：取消一次卡住的 478 条任务后重启，`processing 174 → 0`，
`stale` 回到 202 —— 与文档记录的"172 截断 mp3 + 25 APE + 5 其它"吻合。

**结论**：这 202 条是历史上已知的截断/损坏文件，重试仍会失败。是否删除或移出待索引清单，需要拍板。

## 十、一个需要你知道的副作用

那 178 条已知坏文件现在处于 `pending`。**每次启动应用，自动补索引都会试着重跑它们**
（数量没到 2000 的阈值，不会拦），大约会占用 GPU 十几分钟，然后再次失败。

这不是 bug，是"失败无限重试"的老行为。要根治需要给工件加**重试预算**（attempts 列 +
permanent 标记 + 清理入口），属于数据结构改动，我没有擅自做。

你决定这 202 条怎么处理后，这个副作用自然消失：
- 删掉 → 索引里也不再有记录
- 移出待索引 → 需要加一个"跳过"状态
- 保留 → 我加`permanent`标记，让它们不再被自动重试

### 二十六、点 S/M 时闪一下且断音（同日 22:10）

用户反馈：点 S 或 M，播放区会闪、声音会断一秒才出来。

**根因**（两条一起）：
1. `applyChannelSelection` 先 `pause()` 再等服务端生成声道混音（新组合首次要解码 + 写 WAV），
   整个等待期间没有声音 —— 这就是「断一秒」
2. 点 S/M 的处理器里调了 `renderChannelStrips()`，整个声道栏 DOM 重建一次，看起来就是闪

**改法**：
1. 顺序倒过来：先在后台把新音源准备好（旧声音继续播），再切 `src`；切换时按已过去的时间补正播放位置
2. S/M 只改按钮自己的颜色（`updateChannelButtonStates`），不再重建 DOM
3. 切 `src` 前先用一个临时 `Audio` 预加载新地址，元数据几乎瞬间就绪
4. 打开声道栏时后台预生成「单独听每条声道」的试听文件（服务端按组合缓存）
5. 连点保护：用 `switchToken` 丢弃过期的切换请求

**实测**（服务端混音耗时）：

```

长曲 dcd007_03.wav       ：首次 0.195s，命中缓存 0.003s
```

配合预生成，点 S/M 时基本直接命中缓存；即使没命中，旧声音也会一直播到新音源就绪，不再出现「先静音再出声」。

**没做到的部分**：真正的零间隙切换需要把多声道播放整个搬到 WebAudio（按声道增益），
但那会让播放/进度/倍速全部重写，而且注释里记过 WebAudio 在部分机器上会崩渲染进程，所以没动。

**根因**：`audibleChannels()` 返回空数组时（S 和 M 同时命中，或所有声道都被静音），
`resolveChannelSource()` 里有一行 `if (!audible.length) return null;`，null 被当成
「用原文件播」，于是整条音轨原样播放。空集合被误读成了「全开」。

**改法**：在 `applyChannelSelection` 最前面判断可听声道数：

```js
const audibleNow = audibleChannels();
if (channelState.count > 0 && audibleNow.length === 0) {
    channelState.silent = true;
    if (audioPlayer) audioPlayer.volume = 0;
    return;   // 不换音源：波形、进度、电平继续走
}
```

配套：
- 解除静音（任一按钮取消 / 点全部可听）时恢复 `currentVolume / 100`
- 静音状态下拖音量条不会被意外解除（`channelState.silent ? 0 : currentVolume / 100`）
- 静音声道的电平条从 0.25 提到 0.45 透明度，静音时仍能看清电平

**为什么用 volume=0 而不是生成静音文件**：生成文件要解码整首再换 src，会有一次卡顿；
volume=0 是瞬时的，波形和电平完全不受影响 —— 正好是「看得到、听不到」的需求。

**验证**：打包产物里确认 `channelState.silent = true` 分支、音量保护、0.45 透明度都在。
### 二十八、断音/闪烁的真正原因：换 src 时在同一个播放元素上（同日 22:50）

用户补充的关键线索：**只有第一次点 S/M 会断音和闪**，之后再点就不闪了。

这条线索指向真正的原因：不是服务端慢，而是**换音源的方式**——
`pause()` → 给同一个 `<audio>` 换 `src` → `load()` → 等元数据 → `play()`。
元素被 `load()` 一清，界面上的进度/时长立刻归零再恢复，就是「闪」；
中间这段等待就是「断一秒」。第二次点击如果可听集合没变，代码里 `if (audioPlayer.src === src) return;`
直接返回，根本不换源 —— 所以不闪也不断。

**改法（换播放元素，而不是换同一个元素的 src）**：

1. 把四个事件（ended / timeupdate / loadedmetadata / error）抽成 `attachPlayerHandlers(el)`，
   每个处理器都带 `if (el !== audioPlayer) return;`，防止旧元素串台
2. 新增 `switchPlaybackSource(src, position, wasPlaying)`：
   在后台新建一个 `Audio`，加载到 `loadedmetadata`、对齐播放位置、设好音量/静音/循环/倍速，
   **再**把它设成当前 `audioPlayer`、立刻暂停旧的并清空其 `src`，最后 `play()`
3. `applyChannelSelection` 里旧的 pause→src→load 整段删掉，改为调用上面这个函数，
   并把等待期间流逝的时间补到播放位置上

效果：正在显示的那块界面（波形、进度条、时长）从头到尾没被重置，所以不闪；
旧声音一直播到新元素就绪才停，所以不再是「先静音一秒」。

**验证**：把 index.html 里两段内联脚本抽出来用 node --check 做过语法校验（都通过）；
重启后界面正常渲染（文件列表、波形、常用条都在）。
**未验证**：实际的听感（我没法在这台机器上点按钮），需要用户实测。

### 五十七、mel 卡死根治：给管道写加超时（10-30 23:40）

**定位**：`_mel_round_trip_locked` 里 `w.stdin.write(payload)` 是**阻塞写且没有超时**。
worker 卡死时不再读 stdin，管道缓冲区写满后这行会**永久阻塞**，
后面的「读超时 → kill → 重试」逻辑根本没机会执行 —— 这正是用户报的
「父任务停在 36949/36950 十九分钟、worker 烧 3888 秒 CPU」。

**改法**：写放到线程里，带 5~15 秒看门狗（按批次超时的 1/4，夹在 5~15s 之间）；
超时就 kill 重启 worker 再重试，日志打 `mel_round_trip write blocked >Ns`。

**验证**（用假 worker 模拟「stdin 永远写不进去」）：

```
返回 {'a.wav': None}，耗时 19.2s
日志：mel_round_trip write blocked >5s, kill worker and retry
PASS
```

改之前这种情况会一直挂着不返回；现在两次尝试后放弃并返回失败，父任务能继续往下走。

注：worker 内 C 扩展死锁本身仍无法从 Python 侧中断，
但「写阻塞」这条真正的挂死路径已经堵上，剩下的由父进程 kill + 二分定位处理。
